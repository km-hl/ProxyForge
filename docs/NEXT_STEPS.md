## 审查结论与修正

原计划方向合理，列举的后台阻塞、缓存并发写、环境代理、root 容器和依赖未锁问题在当前代码中仍存在。需要调整以下设计与顺序：

| 问题 | 代码依据与修订结论 |
| --- | --- |
| 只把刷新改成 `to_thread` 不够 | `main.py` 的后台刷新、`/sub`、机场修改及全局导入共享缓存。线程化前先完成锁、失效版本及文件提交保护，避免放大竞争；同步磁盘操作也应离开事件循环。 |
| 单次请求汇总一次写不能彻底防丢数据 | 两个 `/api/airports/info` 请求仍可能各自覆盖旧快照。需要跨请求的读最新值、合并、原子替换，以及旧请求不得覆盖新刷新结果的规则。 |
| 原子替换不等于并发正确 | `os.replace` 防半写，不能防更新丢失或机场删除后旧结果回填。复用 `proxyforge/config/template_store.py` 的 `atomic_write`，同时建立提交协议。 |
| `RLock` 不解决缓存失效后回填 | `@cached` 的函数计算通常在锁外；旧计算结束可能重新填入已清空的缓存。所有刷新入口需要同一来源快照/代次检查，锁内不能联网。 |
| 原子写验收承诺过强 | replace 前失败保留旧文件；replace 后目录同步失败可能已是完整新文件。强制终止可能留下临时文件，不能保证 `finally` 总会清理；应用不读临时文件，另定义安全清理。 |
| 安全出站第一阶段不是完整 SSRF 修复 | `trust_env=False` 只解决隐式代理等环境继承，不能关闭 DNS 校验和连接之间的窗口。DNS pinning 保持 P1，并独立验收。 |
| Docker 中 chown 不解决旧挂载目录 | `./data:/app/data` 会遮住镜像内权限。需明确 UID/GID、首次建目录、旧私有文件迁移与回滚，不可只添加 `USER`。 |
| 漏掉已停止上游维护的运行时 | Docker 仍为 `python:3.9-slim`，CI 为 3.9/3.12。新增运行时升级任务，先确定支持矩阵再生成依赖锁。 |
| 结构重构与 schema 变更混在一起容易破坏兼容 | 不硬规定 auth 最先迁移；schema 的内部标准化与外部请求校验分开，保留 400/422、字段与序列化行为。 |
| 文档与发布不能全部等到最后 | Agent 命令依赖固定安装产物，中文文档是持续门禁。现有 README 还含“无模板冲突保护”“全局导入可能部分成功”等过时描述和更新绝对安全的承诺，应提前纠正。 |
| “所有修复补测试”需区分改动类型 | 行为修复必须有有效回归；纯说明翻译做内容、链接、命令核验，无需制造无意义测试。代码 PR 合并前仍须完整 CI 通过。 |

Python 3.9 已于 2025-10-31 结束上游支持，见 [PEP 596](https://peps.python.org/pep-0596/)。这与发行版自行维护其系统 Python 是不同边界。

## 执行原则

- 一个独立问题一个分支/PR，分支默认使用 `codex/`；有依赖时注明基线和合并顺序，不将尚未齐备的并发修复单独部署。
- 不顺手重构，不为减少行数拆模块。默认保持 API、文件格式与订阅语义；必要变更单独设计并说明迁移。
- 行为修复先复现再添加回归，保留现有测试和安全门禁。代码改动须完整 CI 通过。
- 新增/修改的项目说明必须有完整中文版本；旧文档按第 15 项补齐。
- 不输出或提交真实凭据、订阅地址、节点秘密、运行数据和本机交接记忆。必要接口与长期约定同步到本机 `MEMORY.md`，该文件继续 Git/Docker 忽略，永不上传 VPS。
- 区分本地通过、CI 通过、发布、部署与公网验收；本次计划审查不代表后续功能已经实施。

## P0：Airport 稳定性

### 1. 后台机场刷新移出事件循环

依赖第 2–4 项的提交/并发约定。将一次同步刷新封装后交给 `asyncio.to_thread`，涵盖拉取、磁盘读取/合并和提交；保持每批最多 5 个机场并发。

保留启动后等待 300 秒、每轮结束后等待 4 小时的现有调度，而非改成固定整点。避免同一个后台任务重叠执行，保存任务引用并在关闭时处理取消。
取消等待并不会杀死已运行的线程，需使用有界网络等待及停止/代次检查，防止关闭或配置失效后仍发布结果。

验收：用受控阻塞事件而非长时间 sleep 验证刷新中 API 仍响应；覆盖任务启动/关闭、失败下一轮可恢复、来源中途修改、已有缓存补齐与不完整结果不覆盖旧缓存。

### 2. 机场信息缓存按请求汇总、跨请求安全提交

`fetch_single_airport_info` 的网络 worker 只请求和解析，不能读写共享 JSON。调用方先读缓存快照、判定命中/需刷新的条目，再并发获取、合并提交。

- 保持 `GET /api/airports/info?force_indices=all` 或逗号分隔的零基索引、`{"info": [...]}`、原列表顺序与 24 小时缓存期限；现有错误结果也带时间戳并缓存，改变该语义须另说明。
- 锁外联网；锁内重新读取最新缓存并合并本次增量，再原子写一次。不能拿请求开始时的整份旧缓存覆盖其他请求。
- 定义每来源的刷新序号/提交优先级；较早启动的请求晚完成时不能覆盖较新的已接受刷新。
- 以来源配置快照检查机场删除/改 URL 的情况，防旧结果复活。重复 URL、不同显示名需分别保持响应中的名称与顺序，内部复用不能串数据。
- 落盘失败仍返回本次已得到的信息，以脱敏日志报告；不泄露含凭据的 URL。

验收包含同批多机场、两请求交错完成、强制与普通刷新交错、磁盘写失败、损坏缓存、来源修改与旧格式读取。

### 3. 机场缓存原子写与提交边界

至少覆盖 `data/airport_cache.yaml` 和 `data/airports_info_cache.json`，包括 `/sub` 与后台刷新等所有写入口。
优先复用现有 `atomic_write(path, content)`：同目录独占临时文件、0600、flush/fsync、replace、支持的平台同步目录。
JSON/YAML 在调用前完成序列化；只有实际重复时再加薄封装，不先制造三套工具。

- 文件锁/线程锁解决并发读改写，原子替换解决文件完整性，二者不能互相替代。
- 缓存不是模板历史，不进入 `TemplateStore.commit` 的模板事务/历史白名单；若抽取底层工具，保留模板恢复行为和现有测试。
- replace 前失败：旧文件完整；replace 后失败：允许读取完整新文件，需明确提交结果不确定的处理。
- 正常异常清理临时文件；模拟进程终止时保证不会把残留当缓存。清理只能识别本工具产物且不能删除活跃 writer 的临时文件。
- Windows 不承诺 POSIX 目录 fsync；记录平台保证。文件权限不可扩大。

验收覆盖序列化、写入、fsync、replace 和目录同步故障，以及并发读者只看到完整旧/新内容。

### 4. 内存缓存锁、失效代次与来源快照

统一 `threading.RLock` 保护 `TTLCache` 的读取、写入、过期处理、clear 和预热；保留 `maxsize=1`、12 小时 TTL 与正常结果。
范围包括 `get_airport_proxies_cached`、机场保存、全局导入和后台更新。

- 缓存对象不向外暴露无锁访问路径；网络计算放在锁外，提交时重新检查来源代次。仅给 `@cached` 加 `lock=` 不能作为全部完成条件。
- 配置更新增加代次并失效；旧快照产生的内存和磁盘结果均不可提交。必要时有限重试，不能无限重试阻塞请求。
- 明确统一锁顺序：配置锁在前，缓存锁在后；不要持缓存锁调用获取配置锁的函数。来源读取及提交检查必须使用一致快照。
- 当前阶段以单 Controller 进程/单副本为支持边界并在部署说明写明；`RLock` 不是跨进程锁。多 worker/副本需额外的跨进程失效与刷新协调，暂不宣称支持。
- 不用节点列表原地修改污染共享缓存；检查共享对象的所有权/复制边界。

验收使用 Barrier/Event 稳定复现并发读写、clear 后旧结果回填、机场删除/改名/换 URL、全局导入以及后台与 `/sub` 交错。

## P1：安全与可重复部署

### 5. 加强安全出站 HTTP（分阶段 PR）

实施状态：Session 隔离与 DNS pinning 已合并；单次/批次网络时间预算、有界 DNS 等待、慢流中断及回归已实现，预算 PR 待审查合并。默认单次 60 秒、每跳 DNS 10 秒、批次 180 秒、最多 8 个系统解析线程；CPU/锁/磁盘及关闭边界见[出站时间预算](OUTBOUND_BUDGETS.md)。此前接口和 TLS 边界见[机场 HTTP 请求说明](OUTBOUND_HTTP.md)。代码完成不代表已部署或通过真实公网验收。

现有入口为 `proxyforge/security/network_security.py:safe_get`，保留 HTTP/HTTPS 限制、公网地址检查、逐跳校验、3 次重定向和 10 MiB 响应限制。

第一阶段使用受控 `requests.Session` 并设置 `trust_env=False`，确保 Session/response 被关闭，不跨线程共享可变 Session。
除 HTTP_PROXY/HTTPS_PROXY/ALL_PROXY 外，核对 `.netrc` 与环境 CA 配置不再继承的影响；需要自定义 CA 时采用显式可信配置，不关闭 TLS 校验。

第二阶段固定连接到本次解析并验证的 IP，保留原主机名用于 Host、SNI 和证书校验。每次重定向重新执行完整流程；重试/连接池不能偷偷重新解析到未校验地址。
实现前选择可维护的 transport/adapter 方案，禁止全局 monkeypatch DNS 或 `verify=False`。

验收：私有/保留 IPv4、IPv6、localhost、混合公网/内网 DNS 结果、跳转到内网、环境代理、DNS rebinding、证书主机名不符、有效 HTTPS、自定义 CA 边界、大小与重定向限制。DNS pinning 需能观察真实连接目标的受控集成测试，不能只 mock 校验函数。
响应字节限制不等于总耗时限制；审查慢速响应和 DNS 等待，定义单次请求/刷新总预算与退出边界。

### 6. Controller 容器非 root

实施状态：固定10001:10001、私有数据目录、启动权限检查与显式停机迁移工具已实现，新增首启/旧数据/失败/回滚容器验收。操作及平台边界见[非 root 容器说明](CONTAINER_PERMISSIONS.md)。第6项已通过容器验收并合并；随后推进第5项 DNS pinning 与总耗时预算。

固定并记录专用 UID/GID，以非 root 启动 `uvicorn main:app`，保持端口和数据路径。Controller 不增加 runtime/helper 权限。
镜像内权限设置不能替代 bind mount 迁移：提供首次启动目录准备及旧数据停服迁移步骤，先备份、核对路径，再仅修正 ProxyForge 数据所有权，不跟随符号链接操作目录外文件。
保留私有文件权限，不使用 777，不把所有文件改为全局可读；权限不足时给出可操作错误，不以 root 自动兜底运行服务。

验收：实际容器非 root、空 data 首启、config/admin token、模板/历史、SQLite/WAL、deployment.key、机场缓存、重启、旧 root-owned data 升级、迁移失败与回滚。全部在隔离副本验证。

目标流程：**添加服务器 → 显示并复制安装命令 → VPS 执行 → 隐藏输入一次性注册凭据 → 服务启动 → 控制台显示心跳**。

1. 中文文档先提供从固定完整 commit 获取源码到安装、检查服务的完整命令块；不能只给需要用户预先找到源码目录的相对路径。

接口与安全边界：

- 复用 `POST /api/agents/registration-tokens` 获取一次性凭据/到期时间、`POST /api/agent/register` 注册和 `POST /api/agent/heartbeat` 回报。命令生成不意味着需要新增注册/远程 shell API。
- 命令自动带入并允许核对合法公网 HTTPS Controller 根地址；反向代理场景不能盲信客户端 Host/转发头，允许管理员显式配置可信地址。URL 用严格校验与 shell 参数转义，浏览器以文本显示。
- 一次性凭据保留当前 10 分钟有效期与单次消费；不嵌入可复制命令、URL、参数、日志或持久化浏览器存储。继续通过隐藏 TTY 输入/标准输入传递；注册结果丢失沿用孤儿记录清理和新凭据恢复流程。
- 下载 URL 固定版本/完整 commit；使用随可信版本提供的预期 SHA256 校验。不能仅从同一个任意镜像同时取包和 hash 就宣称来源认证。下载、校验、解包成功后才以 root 执行；失败停止，不继续注册。
- 固定 bootstrap 自身的版本和信任来源；校验完整安装包路径/成员及 root 执行代码的所有权。不能只下载依赖同目录其他文件的 `agent/install.sh` 就运行。
- 默认安装普通 Agent。另给“启用托管 runtime”明确操作/命令，复用同一可信版本的 `agent/install-runtime.sh`，不暗中启用高权限 helper。
- 继续拒绝覆盖现有安装；首次安装、升级、重装和卸载分别给中文命令/指南，不因追求一键体验删除凭据、实例 ID 或运行中配置。
- 支持矩阵以现有 Debian 12/13、Ubuntu 22.04/24.04、amd64/arm64 为基础；每项列明验证状态，不把脚本允许运行误写为全部实测。

验收：从空白测试主机用 UI 复制出的真实命令完成安装与心跳；覆盖下载/哈希/解包失败、过期或重复凭据、注册结果丢失、已有安装、错误平台、命令注入、凭据不进 history/进程参数/日志。区分服务启动与已收到心跳；helper 仍需本地明确启用。不在生产主机执行破坏性安装矩阵。

## P2：结构、模型和错误处理

### 8. 提取 AirportService

完成 P0 并稳定后，优先建立最小 `proxyforge/airports/` 边界；按实际职责决定 service/cache/parser 文件数量。
迁移机场解析、拉取、合并与缓存编排；注入 sources、cache path、HTTP client、clock 及必要提交协调依赖。
模块不导入 `main`、不依赖 FastAPI Request/Response、管理 session 或全局 app。保留内部库导入无副作用，不改变 provider、缓存格式和 UI。

### 9. 逐步整理 FastAPI Router

先迁移已完成服务隔离、依赖较少的路由，建议 airports 试点，再评估 nodes/templates/subscriptions/auth；不把鉴权强定为第一步。
现有 Agent 路由已位于 `proxyforge/control/`，不要重复搬迁制造第二套路由体系。
每个 PR 注入明确依赖，保留 path/method/status/body、鉴权、cookie 同源校验、限速、模板事务/冲突与缓存失效行为，避免循环 import。

### 10. AirportSource schema

先给内部来源快照建立类型，兼容旧 URL 字符串和 `{name, url}` 对象；读取标准化但不自动重写磁盘数据。
外部 API 收紧校验另做明确变更：不能直接将 `List[Any]` 换成模型列表，导致旧字符串、未知扩展字段、400/422 或 URL 序列化悄悄变化。
保留命名、顺序、provider 索引和模板引用，沿用安全 URL 检查；覆盖旧配置、旧 API 客户端和全局导入。

### 11. 收窄异常捕获并脱敏

按 YAML、Base64、JSON cache、元信息分别处理预期异常；回退解析属于正常分支时避免噪声日志。
缓存损坏与写失败记录脱敏诊断；不记录原始异常中可能携带的 URL、完整 YAML、token、节点凭据或私钥。
保留合理的顶层异常边界以避免后台任务永久退出，不把所有 `except Exception` 机械替换掉；不吞取消、KeyboardInterrupt/SystemExit。
每类修改单独复现验证，确保合法订阅解析和现有回退保持兼容。

## 推荐执行顺序与阶段门禁

1. **稳定性阶段：4 → 3 → 2 → 1。** 先确定共享提交/失效协议，按小 PR 实现；整个 P0 验收后再部署，避免中间状态放大竞争。
2. **安全与构建阶段：5 第一阶段 → 17 → 7 → 6 → 5 第二阶段。** DNS pinning 仍为 P1，发布记录明确未关闭的窗口，不因结构重构而推迟。
3. **文档与安装阶段：15 持续执行；14 的固定产物准备 → 16。** 可与前两阶段分开推进小型工作，不依赖 P2 重构；安装相关安全前置必须完成。
4. **结构阶段：8 → 10 内部标准化 → 9；11 按实际问题穿插。** 外部 schema 收紧单列兼容变更，避免与搬文件混合。
5. **仓库与发布阶段：12、13 独立安排；14 完善正式 Release。** 所有计划项完成与否均在对应 PR/发布记录中标明。
