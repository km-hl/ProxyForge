# 机场节点缓存并发与失效

本次实现[下一阶段计划](NEXT_STEPS.md)的第 4 项：内存缓存锁、失效代次与来源快照。
机场信息 JSON 汇总、缓存原子写和后台 `to_thread` 分别属于后续独立任务，本次不视为已完成。

## 支持范围

Controller 目前按**一个进程、一个副本**运行。使用默认 `uvicorn main:app`/Docker 启动入口，不启用多个 worker，不让多个 Controller 共享同一 `data/`。
线程锁保护同进程请求和后台刷新；模板文件锁本身具有跨进程能力，但不代表内存缓存、失效代次与后台调度已经支持多进程。
直接修改运行文件的外部程序不属于受协调的配置写入接口。

## 行为与接口

HTTP 路径、正常请求响应、订阅格式和运行文件路径保持不变。内存缓存仍只有一项，TTL 为 12 小时；空拉取结果也遵循原有缓存规则。
后台启动延迟 300 秒，每轮结束等待 4 小时，每批最多 5 个机场请求。本次仍同步执行后台刷新，事件循环隔离将在第 1 项完成。

- `POST /api/airports` 与 `POST /api/template/import` 完成请求与引用校验后，在配置锁内失效缓存，再提交配置。存储层检查或提交失败仍可能发生在失效之后。
- 拉取使用一个固定来源快照，联网时不持有配置锁或内存锁。读写缓存前重新检查配置与失效代次，拒绝过时结果。
- `/sub` 和 `/api/proxies` 最多尝试两个快照。连续发生来源变更时返回不含订阅 URL 的 503，客户端稍后重试；不会无限循环或把旧结果当新来源发布。
- 后台成功刷新会预热缓存并推进代次，阻止早先开始的订阅拉取覆盖新结果。后台结果过期时直接丢弃，等待下一轮。
- 返回节点使用深拷贝，调用方修改列表或嵌套字段不会污染下一次缓存命中。
- 磁盘缓存读取、合并与受快照检查的提交参与同一个配置锁；磁盘节点写入失败仍可返回已得到的节点，不扩大原有缓存失败的影响范围。

`main.py` 内部接口：`airport_cache_snapshot()` 返回来源及代次；`airport_cache_locked(snapshot)` 固定配置锁→内存锁的顺序；`get_airport_proxies_cached(snapshot=None)` 读取或计算；`subscription_airports()` 合并回退并有限重试；`refresh_airport_cache()` 执行一次后台刷新。
`save_cache_to_file(proxies, snapshot)` 必须携带快照，不能绕过检查。`_subscription_cache` 为内部对象，所有访问必须在统一锁内。应用外部 HTTP API 不受这些 Python 接口调整影响。

## 来源修改与磁盘回退

现有 `airport_cache.yaml` 仅按机场显示名标识来源，无法证明节点属于哪个订阅 URL。因此机场列表、顺序、名称或 URL 变化时，提交新配置前先移除整份旧节点缓存并同步目录（支持的平台）。
这也覆盖换 URL 不换名称和进程重启后的误用；来源完全相同的保存/导入保留磁盘回退，只失效内存缓存。

这一安全修正的代价是：来源变化后需要重新拉取；若其他机场此时故障且没有有效备用节点，订阅仍按现有行为返回 422。配置提交失败时缓存也可能已清空，但旧配置仍按模板事务规则保留或恢复；缓存可以重新生成。
如果旧缓存无法移除，接口返回 503 并且不开始新配置提交。已经持久化提交日志后的失败仍按原有恢复协议处理，不宣称配置一定未改变。

## 升级与回滚

无需数据库迁移、文件格式迁移或 Agent/helper 升级。按完整 P0 发布步骤升级 Controller，保留既有数据与凭据。
代码回滚使用配套旧 Controller 版本；无需恢复旧机场节点缓存。旧版本会重新暴露缓存并发问题，因此不应把回滚作为长期运行方案。
