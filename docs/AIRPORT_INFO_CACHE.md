# 机场信息缓存：批次汇总与并发提交

本文对应[开发计划](NEXT_STEPS.md)第 2 项，基于已完成的[节点缓存并发保护](AIRPORT_CACHE_CONCURRENCY.md)与[缓存原子写入](AIRPORT_CACHE_ATOMIC.md)。
Controller 仍按单进程、单副本运行；没有新增 HTTP 路由、数据库迁移或 Agent 能力。

## 接口与兼容行为

`GET /api/airports/info` 保持管理鉴权，返回 `{"info": [...]}`，条目顺序与机场配置一致。
每个条目仍包含 `url`、`name`、`nodesCount`、`upload`、`download`、`total`、`expire`、`error` 和完成时间 `_timestamp`。

- `force_indices=all` 强制刷新全部来源；逗号分隔的零基索引只强制指定条目。原有空白、越界索引和无法解析参数的处理保持兼容。
- 正常及失败结果仍缓存 24 小时；到期或被强制刷新才重新请求。网络失败以异常类型填充 `error`，不把原始异常内容返回客户端。
- 相同 URL 在一个请求中只拉取一次。如果它的任何一个索引被强制刷新，该 URL 的所有别名使用同一次新结果；响应按每条配置分别覆盖显示名，保持顺序。没有自定义名时使用远端文件名或主机名。
- 新落盘的 `info.name` 使用不含本地别名的远端名称；返回副本再应用自定义名，避免同 URL 的机场别名互相污染。旧结构仍可读，旧条目缺失内层 `_timestamp` 时使用外层时间戳补齐。

磁盘仍为 `data/airports_info_cache.json`，结构继续是 URL 到 `{info, _timestamp}` 的映射；序号和代次仅存在于进程内，不写入文件。

## 拉取与提交流程

1. 在配置锁内读取来源快照、信息缓存代次和文件，分配递增请求序号，按 URL 去重，选出过期/未命中/强制刷新的条目。
2. 释放锁，以最多 5 个 worker 并发拉取。`fetch_single_airport_info(item)` 只负责 HTTP 请求、解析和生成结果，不读写任何共享缓存。
3. 全部 worker 完成后重新取得配置锁，确认来源快照和信息代次仍有效，并重新读取最新缓存。
4. 仅合并本请求的新结果。每个 URL 记录最后接受的刷新请求序号；较早请求晚完成时不能覆盖较新的结果。不同 URL 的刷新合并到最新文件中，避免覆盖其他请求。
5. 有可接受更新时统一原子写一次；全部命中或全部新结果已过时则不写。响应使用独立副本。

较新结果在尝试写磁盘前即登记序号。即使这次写入失败，也不允许较旧请求覆盖可能已经完成 replace 的新文件。若旧结果被拒绝，优先返回最新磁盘结果；磁盘也不可用时仍可返回该请求已取得的信息，但不把它再次持久化。后续新请求可继续刷新。

内部接口：

- `load_airport_info_cache()`：读取、验证和兼容旧缓存条目。
- `save_airport_info_cache(data)`：在配置锁内原子落盘，失败仅记录脱敏诊断。生产写调用由请求汇总层发起。
- `fetch_single_airport_info(item)`：网络 worker，移除旧 `force` 参数；缓存策略统一由 `get_airports_info(force_indices)` 决定。

测试和本地运维 Python 调用需要使用新的职责边界；公开 HTTP 参数不变。不要从 worker 调用缓存保存函数。

## 来源变化与失败恢复

机场配置变化时，在配置事务提交前同时失效节点 YAML 和信息 JSON 缓存，并推进独立的信息缓存代次、清理每 URL 序号。来源内容不变的保存/导入保留信息磁盘缓存。
来源 A→B→A 也会使最初的 worker 失效；节点后台预热只改变节点缓存代次，不中断正在拉取的机场信息。

刷新途中发现来源改变会重新获取当前来源，最多尝试两个快照。持续变化则返回脱敏 503，请稍后重试；删除机场后旧 worker 不会把它写回文件。配置变化导致磁盘清理失败时沿用 503，并且不开始新配置事务。

损坏 JSON、错误的顶层类型或损坏条目不会导致请求崩溃：保留可用条目，缺失项重新拉取。无效数值、未来/非有限时间戳、缺失基本字段视为损坏；日志不包含 URL、缓存正文或底层异常消息。旧缓存中已不在当前来源列表的条目在下一次有效写入时移除。

磁盘写入失败仍返回已获得结果；持久化为 best effort，不承诺写失败后下一次请求一定命中这次结果。原子写仅提供单文件保证，不构成配置文件与缓存的多文件事务。

## 验证

`tests/test_airport_info_concurrency.py` 用 Barrier/Event 稳定复现同批丢条目、跨请求覆盖和旧请求晚完成，覆盖单次汇总写入、worker 无缓存读写、URL 去重与别名、24 小时 TTL/错误结果、force 参数、鉴权/响应字段、旧缓存、损坏缓存、来源保存/导入、A→B→A、有界重试、后台预热独立性，以及写失败后旧请求不得覆盖。
原子写故障、子进程终止和权限测试仍保留；其机场信息入口改为调用汇总层，使实际生产落盘路径继续受检验。

## 升级与回滚

无需转换运行文件或修改 schema，升级完整 Controller 即可。首次读取合法旧缓存继续命中；机场配置变化后的重新拉取可能暂时增加出站请求。
回滚到配套旧 Controller 代码/镜像即可，不还原旧缓存或用户配置，但会重新暴露信息缓存丢更新的问题。
下一项是后台刷新线程化及生命周期管理；完整 P0 验收前不部署中间版本。
